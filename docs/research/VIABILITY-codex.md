# Viability and reliability assessment

Research date: 29 October 2026. This is desk research, not a device test. Scope: non-rooted Android 11–16, ADB shell uid 2000, and an `app_process`-style service. OEM- and build-specific claims require device testing; unestablished claims are marked **UNVERIFIED**.

## Decision

**VERDICT: Viable-with-limits.** Go for a research prototype on qualified devices and apps. No-go for a general promise that arbitrary apps can be tested invisibly and reliably while the owner uses the same phone normally. Scrcpy already creates and streams a new virtual display and launches apps without root on supported devices. That establishes feasibility, not an Android-wide contract or an isolated second user session. [scrcpy](https://github.com/Genymobile/scrcpy), [virtual display guide](https://github.com/Genymobile/scrcpy/blob/master/doc/virtual-display.md).

The defensible initial product is a supervised developer tool for a spare or explicitly qualified phone, with a published model/build/app matrix. A separate display shares the phone's user, apps, accounts, settings, resources and much of its input infrastructure.

## Technical premise

### Display and activity placement

A virtual display renders to a `Surface` that can feed an encoder without appearing on the physical screen. `PUBLIC` and `OWN_CONTENT_ONLY` control display visibility and mirroring; they do not themselves grant trusted-display privileges or guarantee third-party launches. Auto-mirroring and secure capture have separate permission requirements. Android restricts activity placement on non-system virtual displays to reduce covert capture; display ownership, activity embedding, trust and the caller's privileges matter. Shell is privileged compared with an ordinary application, but is not root and its grants can vary. [DisplayManager](https://developer.android.com/reference/android/hardware/display/DisplayManager), [AOSP activity launch policy](https://source.android.com/docs/core/display/multi_display/activity-launch), [AOSP testing environment](https://source.android.com/docs/core/display/multi_display/testing-dev-environment).

Scrcpy requests PUBLIC and OWN_CONTENT_ONLY, internal TRUSTED on Android 13+, and additional focus/display-group flags on Android 14+. These flags and reflected APIs are implementation details, not stable public shell guarantees. A Pixel running Android 15 QPR2 Beta 1 rejected trusted-display creation with `Requires ADD_TRUSTED_DISPLAY`; that is evidence for that build, not proof that all Android 15 devices fail. Subsequent scrcpy releases support newer devices. [scrcpy display code](https://github.com/Genymobile/scrcpy/blob/master/server/src/main/java/com/genymobile/scrcpy/video/NewDisplayCapture.java), [issue 5523](https://github.com/Genymobile/scrcpy/issues/5523), [releases](https://github.com/Genymobile/scrcpy/releases).

Android 10+ desktop/freeform and `force_desktop_mode_on_external_displays` are device/developer configuration, not a privilege grant or a universal prerequisite for virtual-display activity launch. Launcher, decorations and window sizing vary; scrcpy notes that some devices have no launcher on the virtual display. The setting's exact availability and effect across Android 11–16 and OEMs are **UNVERIFIED**. Avoid automatically changing global developer settings. [AOSP decorations](https://source.android.com/docs/core/display/multi_display/system-decorations), [scrcpy guide](https://github.com/Genymobile/scrcpy/blob/master/doc/virtual-display.md).

`am start --display ID` requests placement; export rules, launch modes, task affinity and display security still apply. Android may move an existing activity/task to the requested display, disrupting the owner if they are using that app. A second display does not create a second app-data sandbox. Android 10+ can resume activities on multiple displays simultaneously, but focus, visibility, occlusion, exclusive resources and OEM behavior still influence lifecycle. [AOSP launch policy](https://source.android.com/docs/core/display/multi_display/activity-launch), [multi-resume](https://source.android.com/docs/core/display/multi_display/multi-resume), [FAQ](https://source.android.com/docs/core/display/multi_display/faq).

### Input, capture and hierarchy

Android 14 AOSP `input` supports `-d DISPLAY_ID` for taps, swipes, key events and text. Scrcpy sets event display IDs and calls the hidden `InputManager.injectInputEvent` API. Injection is permission- and OEM-dependent. Target every event explicitly and stop if the display disappears or injection fails. Text composition, Unicode, navigation keys and focus require separate tests. Xiaomi may require an additional USB debugging security setting, and it is not guaranteed to fix every device. [AOSP input command](https://android.googlesource.com/platform/prebuilts/fullsdk/sources/+/refs/heads/androidx-compose-integration-release/android-34/com/android/server/input/InputShellCommand.java), [scrcpy input wrapper](https://github.com/Genymobile/scrcpy/blob/master/server/src/main/java/com/genymobile/scrcpy/wrappers/InputManager.java), [scrcpy FAQ](https://github.com/Genymobile/scrcpy/blob/master/FAQ.md).

The strongest capture path is the surface supplied to the virtual display, as in scrcpy, with frames extracted from the stream. `screencap -d` exists, but AOSP refers to SurfaceFlinger display identifiers and physical displays: a logical display ID is not necessarily the required identifier. Its ability to capture this particular virtual display is **UNVERIFIED**. SurfaceControl approaches use internal APIs and are version/permission sensitive. Secure or DRM content may be blank or unavailable. [AOSP screencap](https://android.googlesource.com/platform/frameworks/base/+/master/cmds/screencap/screencap.cpp), [scrcpy capture](https://github.com/Genymobile/scrcpy/blob/master/server/src/main/java/com/genymobile/scrcpy/video/NewDisplayCapture.java), [Android secure windows](https://developer.android.com/security/fraud-prevention/activities).

Do not assume classic `uiautomator dump` returns a complete tree for the secondary display. `UiAutomation.getWindowsOnAllDisplays()` and accessibility window display IDs provide a possible per-display path with interactive-window retrieval; availability and semantic completeness remain conditional. Appium UiAutomator2 documents display and multi-window selection, but its exact behavior with this display must be tested. React Native accessibility labels and Flutter semantics depend on the app. [UiAutomation](https://developer.android.com/reference/android/app/UiAutomation), [AccessibilityWindowInfo](https://developer.android.com/reference/android/view/accessibility/AccessibilityWindowInfo), [Appium multi-display](https://appium.github.io/appium-uiautomator2-driver/latest/guides/multiwindow/).

## Reliability

* **IME and focus:** Android uses a shared IME. It supports local, default-display and hidden policies; scrcpy says its virtual-display IME appears on the default display by default and offers a local policy. Local support depends on trust and OEM behavior and does not prove independent simultaneous text sessions. AOSP warns against per-display focus on regular devices. [IME](https://source.android.com/docs/core/display/multi_display/ime-support), [focus](https://source.android.com/docs/core/display/multi_display/displays), [scrcpy IME](https://github.com/Genymobile/scrcpy/blob/master/doc/virtual-display.md).
* **Lifecycle and system UI:** Multi-resume is possible, not guaranteed under all focus and visibility states. Notifications, permission prompts, authentication, choosers, external links and calls may interrupt the primary screen; exact placement per flow is **UNVERIFIED**. Existing tasks can move between displays. Scrcpy normally destroys content on display close; its alternative moves it to the main display. [launch policy](https://source.android.com/docs/core/display/multi_display/activity-launch), [scrcpy teardown](https://github.com/Genymobile/scrcpy/blob/master/doc/virtual-display.md).
* **Audio and shared resources:** Audio focus and routing, volume, camera, microphone, clipboard, accounts, network and system settings are shared. Test audio can interrupt the owner; muting the device can affect their media. AOSP notes no generic separate targeted audio solution in its multi-display FAQ. [AOSP FAQ](https://source.android.com/docs/core/display/multi_display/faq).
* **OEM and release churn:** Pixel is an AOSP-adjacent baseline but updates can revoke shell capabilities. Samsung One UI/DeX may change windowing; Xiaomi HyperOS/MIUI has documented extra input authorization; OnePlus/Oppo ColorOS behavior is **UNVERIFIED**. Qualify exact models and builds, not brands. Test Android 11–12, 13, 14, 15 and 16 separately. The Android 15 beta permission regression and scrcpy Android 16 audio fix show real churn, not a complete version compatibility matrix. [issue 5523](https://github.com/Genymobile/scrcpy/issues/5523), [releases](https://github.com/Genymobile/scrcpy/releases).
* **Power and transport:** Extra rendering, encoding and Wi-Fi can consume battery and cause heat or throttling; magnitude is **UNVERIFIED**. Wireless ADB can disconnect on network or device changes. Google documents historical dropouts and newer Wi-Fi 2.0 improvements, whose availability on a particular device is **UNVERIFIED**. [wireless debugging](https://developer.android.com/studio/command-line/adb#wireless), [ADB Wi-Fi 2.0](https://developer.android.com/blog/posts/introducing-fast-and-reliable-wireless-debugging-with-android-debug-bridge-adb-wi-fi-2-0).

## Security and policy

Authorized ADB offers broad device access; it is not confined to the test app. A compromised host or agent can inspect sensitive UI, inject actions and act on user accounts. Obtain informed device-owner consent, restrict controller and network access, use disposable test accounts, minimize and redact screenshots, logs and hierarchy data, and provide an immediate stop and ADB revocation path. Do not bypass protected content, authentication or OS permissions. [ADB authorization](https://developer.android.com/studio/command-line/adb), [AOSP display security](https://source.android.com/docs/core/display/multi_display/activity-launch).

Accessibility services and Play-distributed companion apps may invoke disclosure, consent and permitted-use requirements; review the current policy for the chosen distribution. Third-party terms, privacy law, enterprise device policy and AI-provider data processing can restrict automation or artifact uploads. Scrcpy is Apache-2.0; check attribution and each dependency's license. [Google Play accessibility policy](https://support.google.com/googleplay/android-developer/answer/10964491), [scrcpy license](https://github.com/Genymobile/scrcpy/blob/master/LICENSE).

## Users and alternatives

Likely users include mobile developers diagnosing OEM-specific bugs, small QA teams, accessibility/agent researchers and maintainers needing real radios, sensors or GPU behavior. The attraction is local physical-device fidelity and reuse of hardware; demand and willingness to pay are **UNVERIFIED**. A dedicated spare phone provides similar fidelity with fewer personal-session hazards. Emulators provide reproducible snapshots, isolation and CI parallelism; device farms offer broader model coverage and managed concurrency for a fee. This is a useful supplement for supervised real-device debugging, not a replacement for either in reliable CI.

## Top five risks

1. Owner interference through shared focus, IME, tasks, prompts and audio.
2. Hidden API, permission and OEM changes break functionality after updates.
3. Stale display IDs or focus changes cause actions in the wrong context.
4. Protected pixels, missing semantics and external/system flows make tests incomplete.
5. Shared-device battery, thermal, disconnect, state mutation and privacy costs undermine repeatability.

## Cheapest one-day proof of concept

Use one non-rooted phone, a computer, current official scrcpy and platform-tools, wireless debugging, and a disposable test account. Record model, Android build, scrcpy version, settings and test-app version. Use a simple app with a visible counter, text field, button, lifecycle logging and a permission request, plus a different benign app on the physical screen. No framework implementation is needed.

1. Pair ADB and verify `adb shell id` is shell. Run `scrcpy --new-display=1080x1920/420 --start-app=<test.package> --no-audio`; record success and the logical display ID from scrcpy. Confirm the test app appears in the stream while the owner uses the physical display.
2. Run `adb shell input -d <ID> tap X Y`, swipe and text on known controls. Simultaneously tap and type on the physical screen. Record both displays, focus, IME, lifecycle and any misplaced input. Repeat with `--display-ime-policy=local`; record errors or keyboard appearance on the main display.
3. Save stream frames. Separately try `adb exec-out screencap -d <ID> -p` and validate the decoded image and content, not just exit status. Inspect display-specific accessibility windows with an existing compatible Appium setup if available; otherwise mark hierarchy **UNVERIFIED**. Exercise a permission request, external link, notification and audio and record owner-visible effects.
4. Run a repeated flow during 30 minutes of foreground usage; record successes, interruptions, lifecycle and wrong-target events. Disconnect Wi-Fi or stop scrcpy, observe teardown and reconnect. Measure battery and temperature if available; do not extrapolate from one phone.

**Go for a qualified prototype** if creation, launch, repeated targeted touch/text, usable frames and adequate per-display hierarchy work and the defined test causes no owner-visible interruption or wrong-target input. **Kill the original hands-off promise** if main-display input, IME/focus disruption, task movement or an unavoidable prompt occurs. A failure qualifies out that device/build, not necessarily the whole approach; one successful phone does not establish cross-OEM reliability.
